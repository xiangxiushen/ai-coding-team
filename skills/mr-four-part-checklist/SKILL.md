# MR 四段自检（Four-Part Checklist）

> 本 skill 规定**任何 MR（代码 / 文档 / 规则）的描述必须按四段写，一段不缺**。缺段直接判「要求修改」，不进入实质评审。
> 借鉴 mitabase-workspace 的 MR 四段自检，四条一一对应最常见的返工根因；原为仓库规范，现作为可执行 skill 挂 TechLead / Dev。

## 是什么 / 何时用

把「一份合格的 MR 描述长什么样」固化成硬性四段 + 一条红线，消灭「改 A 漏 B」「引用不存在的编号」「断言超出验证范围」三类高频返工。

**用**：TechLead 建 MR 前、Dev 提交分支前，逐段对照本 skill 自检。

## 四段（缺一不可）

### 1. 根因单

单独一行写关联 issue 标识（Multica issue 的 UUID 或编号），指向本 MR 要解决的问题。没有承接 issue 先确认挂靠哪条，不许裸提。

```
关联 issue: <issue-UUID 或编号>
```

### 2. 口径同步清单

改了某个口径 / 决策 / 接口 / 约定，就给出**同主题全仓检索**的命令与命中文件清单，逐一说明「已同步」或「不同步」：

- 已同步 → 列出文件
- 不同步 → 必须写**理由 + follow-up 单号**

**禁止**「改 A 处、B 处旧代码没同改」。

### 3. 引用可回查

描述里每条事实断言（命令 / 接口 / 数字 / 字段 / 约定）都附可回查证据——`文件:行` / 命令 / 端点 / MR / issue。引用不存在的编号或文件 = 打回。

> **PRD 引用格式以 skill `mr-traceability` 为准**：`feat` 类 MR 描述须单独一行写 `PRD: docs/prd/<需求id>/PRD.md § FR-x.y`（文件与 FR 编号须真实可回查），并带关联单号。本段只查「有没有写全」，格式与闸门见 `mr-traceability`。

### 4. 安全 fail-closed 声明

凡涉及鉴权 / 信任面 / 密钥 / 凭据的变更，写明缺依赖 / 缺配置时的失败姿态：

- **默认 fail-closed（拒绝 / 报错），不得 fail-open（放行）**
- 确需例外须写明理由并升级

真源见 skill `security-redlines`。

## 红线：断言范围 = 验证范围

MR 描述里的每条**全局事实断言**（如「全源码零引用」「全门禁通过」），其断言范围不得超出实际验证范围：

- 只跑了精简 job 集，就不许写「全部门禁通过」；要列出**未跑的 job**。
- 断言「某配置全仓零引用」，检索范围必须覆盖全部相关仓，不是只看本仓。
- 越界即 P0 打回。

## 完成判据（本 skill 视为已遵守）

- [ ] 四段齐全（根因单 / 口径同步清单 / 引用可回查 / 安全 fail-closed 声明），无缺段；
- [ ] 口径同步清单给出检索命令 + 命中文件 + 逐项「已同步 / 不同步（理由 + follow-up）」；
- [ ] 每条事实断言都附可回查证据，无编造编号 / 文件；
- [ ] 全局断言范围未超出实际验证范围（未跑项已列出）。
