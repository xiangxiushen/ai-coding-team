# 增量实现（Incremental Implementation）

## 是什么 / 何时用

按**薄纵向切片**交付：实现一小片 → 测 → 验 → 提交 → 下一片。不要一口气写完整个功能。每片结束系统都处于可工作、可测试状态。

**用**：任何跨多文件的改动 / 从计划里领下一个任务 / 想一次写超过 100 行还不测的时候。

**不用**：单文件单函数、范围已最小的改动。

## 增量循环

```
实现 → 测试 → 验证 → 提交 → 下一片
```

## 切片策略

- **纵向切片（首选）**：一次打通一条完整路径（DB + API + UI）。
- **契约先行**：前后端并行时，先定 API 契约，再各自对契约开发。
- **风险先行**：最不确定的片先做，早失败早止损。

## 实现规则

- **Rule 0 简单优先**：先问「能跑的最简单方案是什么？」三条相似的重复代码好过一个过早的抽象。
- **Rule 0.5 范围纪律**：只动任务要求的。注意到范围外的改进 → 记下来，不顺手改。
- **Rule 1 一次一件事**：一个增量只改一个逻辑点。
- **Rule 2 保持可编译**：每片结束项目必须能 build、既有测试必须绿。
- **Rule 3 特性开关**：没做完的功能用 feature flag 包住，允许合并但不对用户可见。
- **Rule 4 安全默认**：新代码默认保守、opt-in。
- **Rule 5 可回滚**：增量可独立 revert，新增优先于修改，删除与替换分开提交。

## 反自我合理化

| 借口 | 现实 |
|---|---|
| 「最后一起测」 | bug 会叠加，Slice 1 的 bug 让 2-5 全错 |
| 「一次做完更快」 | 快感是假的，出了错 500 行里找不着 |
| 「改动太小不值得单独提交」 | 小提交免费，大提交藏 bug、难回滚 |
| 「顺手把这个重构了」 | 重构混进功能，两者都更难审更难 debug |

## 完成判据

- [ ] 每片单独测过、单独提交
- [ ] 全量套件绿、build 干净
- [ ] 功能端到端按 spec 工作
- [ ] 无未提交残留
