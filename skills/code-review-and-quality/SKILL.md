# 代码评审与质量（Code Review & Quality）

## 是什么 / 何时用

对实现做**五轴评审**（正确性 / 可读性 / 架构 / 安全 / 性能）。只出结论，不改代码。

## 审批标准

一个变更只要**确实提升了整体代码健康度**就放行，不必完美。不因为「不是我这么写的」就卡。它提升了代码库、遵循了项目约定，就 approve。

## 五轴评审

### 1. 正确性
符合 spec 吗？边界（null/空/边界值）处理了吗？错误路径（不只 happy path）？测试真在测该测的吗？有无 off-by-one、竞态、状态不一致？

### 2. 可读性与简洁性
命名描述性且一致？控制流直接？有无「聪明」技巧该简化？**能否用更少的行**（100 行能搞定写成 1000 行是失败）？**抽象配得上复杂度吗**（不到第三个用例别泛化）？有无死代码、空实现、`// removed` 残留？

### 3. 架构
遵循既有模式还是引入新模式？模块边界干净？有无循环依赖？抽象层级恰当？**这个重构是降复杂度还是挪地方**（数读者要记的概念数）？特性专属逻辑泄漏进通用模块了吗？

### 4. 安全
输入校验/清洗？密钥进代码/日志/版本控制？认证授权到位？SQL 参数化？输出编码防 XSS？依赖可信无已知漏洞？

### 5. 性能
有无 N+1 查询？无界循环/无约束抓取？该异步却同步？列表接口分页？热路径大对象创建？

## Severity 标签（必须标）

| 前缀 | 含义 | 作者动作 |
|---|---|---|
| **Critical:** | 阻断合并 | 安全漏洞、数据丢失、功能损坏，必改 |
| *(无前缀)* | 必须改 | 合并前处理 |
| **Nit:** | 轻微可选 | 格式/风格，可忽略 |
| **Optional:** | 建议 | 值得考虑不强制 |
| **FYI** | 仅信息 | 无需动作 |

**先讲重点**：正确性和安全优先，其次结构回归和可简化项，最后其他。别用一堆 cosmetic nit 淹没真正的问题。

## 结构性建议（只指问题不够，要给出改法）

一串条件 → 类型化模型/dispatcher；重复分支 → 合并；编排与业务混杂 → 分开；特性逻辑进共享模块 → 挪回；复用 canonical helper；删纯转发 wrapper；提取 helper/拆大文件。

## 变更尺寸

`~100 行` 好 / `~300 行` 单一逻辑可接受 / `~1000 行` 太大，要求拆。
拆分：Stack（顺序依赖）/ 按文件组 / 横向（先共享件）/ 纵向（全栈薄切片）。
**重构与功能分离**：既重构又加功能 = 两个变更，分开提。

## 诚实评审

- **不橡皮图章**：没证据的「LGTM」帮不了人。
- **不软化真问题**：会炸生产的 bug 直说，别写「可能有点小问题」。
- **能量化就量化**：「这个 N+1 每项加 ~50ms」优于「可能慢」。
- **对问题直接反驳**：谄媚是评审的失败模式。
- **优雅接受 override**：作者掌握全上下文且不同意时，尊重其判断。

## 依赖审查五问

新增依赖前问：现有栈能否解决？多大？活跃维护吗？有无已知漏洞？许可证兼容吗？**优先标准库和现有工具**，每个依赖都是负债。

## 反自我合理化

| 借口 | 现实 |
|---|---|
| 「能用就行」 | 不可读/不安全/架构错的代码，债务复利增长 |
| 「我写的所以对」 | 作者对自己的假设盲目，每个变更需要第二双眼 |
| 「以后再清理」 | 以后从不会来，评审就是质量门 |
| 「AI 生成的应该没问题」 | AI 代码要更严，不是更松 |
| 「测试过了就行」 | 必要不充分 |
| 「这重构更干净了」 | 挪复杂度不是降复杂度 |
