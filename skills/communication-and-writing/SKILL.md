# 沟通精简 + 写作规范（Communication & Writing）

> 全体成员通用。借鉴 mitabase-workspace 的「沟通精简」与「writing-style」两条规范，适配中文场景；原为仓库规范，现作为可执行 skill 挂全队。

## 是什么 / 何时用

规定**怎么写评论、怎么回报、怎么下产物结论**：结论先行、挑重点、带证据、无 AI 腔。凡在 issue 评论、MR 评论、产物文档里写字，都适用。

**用**：任何评论 / 回报 / 评审结论 / 产物正文。

## 一、沟通精简（评论 / 回报 / 评审结论）

每条 issue 评论区 / MR 评论区的回复，一律精简、挑重点、讲结论：

1. **结论先行**：先给结论，再给问题 / 判断。抬头 = 结论 + 一句话（≤50 字）+ 要点（≤6 条），详情在后，不埋末尾。
2. **挑重点**：短句 / 列表，一条一动作；不复述上游与前文；通过类只留「评审通过，待合并」；总长尽量 ≤10 行。
3. **带证据**：需要时带 `文件:行` / 命令 / 端点 / MR / issue 链接；无证据的判断先不给。

## 二、写作规范（产物正文 / 文档）

- **朴素用词**：忌「战略 / 赋能 / 打造 / 全面 / 深度 / 助力」等空话套话，面向同事说话。
- **无 AI 腔**：不堆砌、不铺陈、不用「首先其次最后」式八股，一句话能说清不写三段。
- **中文正文，英文标识**：评论、产物正文用中文；文件名、分支名、代码标识符、技术术语保持英文（小写 kebab）。
- **引用可回查**：每条事实断言附证据，拿不准写「待验证」，不把不确定写成已确认。

## 三、@mention 唤起格式（铁律）

在 issue 评论区要**唤起**（派活给）另一个 agent，必须用完整 mention 链接 `[@名字](mention://agent/<uuid>)`。**纯文本 `@名字` 只是普通文字，永远不会唤起任何 agent。**

- 正确（唤起）: `[@Dev](mention://agent/<dev-uuid>) 请写规格`
- 错误（不唤起）: `@Dev 请写规格`
- 只想点名 / 引用、不想唤起时，名字前**不要加 `@`**。
- 拿不到 UUID 就 `multica agent list` / `multica squad get` 查，**先问，不退化纯文本**。

- [ ] 无空话套话 / 无 AI 腔；中文正文 + 英文标识；
- [ ] 每条事实断言附证据，未把不确定写成已确认；
- [ ] 需要唤起 agent 时用了完整 `mention://agent/<uuid>` 链接，未退化为纯文本 `@`。
