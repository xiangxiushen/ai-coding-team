# 任务拆解与计划（Planning & Task Breakdown）

## 是什么 / 何时用

把工作拆成**小、可验证、带验收标准**的原子任务，并按依赖排序。好的拆解是「可靠交付」和「一团乱麻」的分水岭。每个任务要小到能在一次聚焦会话内完成、测试、验收。

**用**：有了 spec 要拆成可执行单元 / 任务太大太模糊无从下手 / 需要多人并行 / 要向人类说明范围 / 实现顺序不明显。

**不用**：单文件、范围明确的改动；或 spec 里已经写好了清晰的任务。

## 核心流程

1. **只读规划**：写码前先读 spec 和相关代码，识别既有模式、映射组件依赖、标注风险。规划阶段不写代码。
2. **画依赖图**：谁依赖谁，自底向上排实现顺序（先地基）。
3. **纵向切片**：一次打通一条完整功能路径（DB + API + UI），不要横向「先建所有 DB、再建所有 API、再建所有 UI」。
4. **写任务**：每个任务带 —— 一句话描述 / 验收标准（可测试）/ 验证方式 / 依赖 / 大概触及文件 / 规模。
5. **排序 + 检查点**：依赖满足 → 每步系统可用 → 每 2-3 个任务设 checkpoint → 高风险任务靠前（fail fast）。

## 任务规模表

| 规模 | 文件数 | 说明 |
|---|---|---|
| XS | 1 | 单函数 / 配置改动 |
| S | 1-2 | 一个组件 / 一个端点 |
| M | 3-5 | 一条功能切片 |
| L | 5-8 | 多组件功能，**要再拆** |
| XL | 8+ | 太大，必须拆 |

**该继续拆的信号**：要超过一次聚焦会话（约 2 小时）／验收标准写不满 3 条以内／触及两个独立子系统／任务标题里出现「和」。

## 并行判断

- **可并行**：独立功能切片、已实现功能的补测试、文档。
- **必须串行**：数据库迁移、共享状态改动、依赖链。
- **需协调**：共享 API 契约的功能——先定契约再并行。

## 反自我合理化

| 借口 | 现实 |
|---|---|
| 「边做边想就行」 | 10 分钟规划省几小时返工 |
| 「任务很明显不用写」 | 写下来才会暴露隐藏依赖和漏掉的边界 |
| 「规划是额外开销」 | 规划本身就是任务，没计划的实现只是打字 |
| 「我脑子里记得住」 | 上下文有限，写下来的计划能跨会话存活 |

## 完成判据

- [ ] 每个任务有验收标准
- [ ] 每个任务有验证方式
- [ ] 依赖已识别且排序正确
- [ ] 没有任务超过约 5 个文件
- [ ] 阶段之间有 checkpoint
- [ ] 人类已审阅并批准计划
