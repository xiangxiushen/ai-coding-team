# 合并门矩阵（Merge Gate Matrix）

> 本 skill 是「**什么变更、过什么门、谁合并**」的**单一真源**。
> Leader 建 MR 前、成员提交前、Reviewer 评审时，都对照本矩阵；**不凭印象放行**。
> 借鉴 mitabase-workspace 的合并门矩阵，适配本小队「代码交付」场景；原为仓库规范，现作为可执行 skill 挂全队。

## 是什么 / 何时用

把「变更类型 → 必过门禁 → 谁合并」固化成一张表，杜绝「忘了过某道门就合并」。

**用**：TechLead 建 MR 前核对门禁；Dev/Product 提交前自检；Reviewer 评审时确认门禁齐备；任何人判断「这个改动该不该放行」。

## 一、铁律（最高优先级，凌驾一切）

1. **Agent 绝不 merge**：所有 MR 的合并动作一律由**人类**执行。TechLead 只建 MR，不点合并。
2. **存在 MR ⟺ 已过门禁**：门禁没过的 commit 不许建 MR（门禁前置）。
3. **治理类改动必须人类共识**：改小队规则、标准、agent 定义、流程的 MR，即使评审通过，也必须人类拍板，不自动合。
4. **含 UI 的变更以 mockup 为基准**：有 UI / 前端页面 / 组件的改动，S3 实现必须对齐 S0 产出的 mockup（PRD 设计段）；无 mockup 不得进入 S3。
5. **PRD 变更必须人类确认才生效**：任何改变需求 / 范围 / 行为的 PRD 修订，未经人类确认，不得驱动下游阶段（防需求悄悄漂移）。
6. **证据优先 / 误判兜底（fail-closed）**：测试与验收结论以**证据**为准。凡证据显示异常，即使自动判定为 PASS，也**一律改判 FAIL**；单测结果以 S3 在 runtime 产出的证据为准，**S4 不复跑单测**。
7. **分支由人类定，一个需求一条分支**：同一需求只用**一条开发分支**（规格 / 架构 / 实现 / 补强同分支迭代，不按阶段新建多分支）；分支 `base` 与 MR `target` 均须**人类明确给出**，agent **绝不自行推导或自选**；未取得 target → **不建 MR**。

## 二、合并门矩阵

| 变更类型 | 必过门禁（叠加） | 谁建 MR | 谁合并 |
|---|---|---|---|
| 新需求 / 需求变更 | **S0 PRD 过 `prd-critic` + 人类确认**（Product 起草 → Reviewer 挑刺 → 人类确认 → 更新 `docs/prd/`） | TechLead | **人类确认** |
| 常规功能代码 | S0 PRD + **S2 架构设计**（命中触发时，Architect 出 `architecture-design.md`/ADR + 人类 approve）+ S2 规格 + S3 TDD（runtime 单测证据）+ **S4 测试**（AC 证据映射 + 通过率硬门 + P0/P1 回归 100% + 误判复核）+ S5 多轴评审（含事实核查复检） | TechLead | **人类** |
| 涉及 DB schema / migration | 多轴评审 + **DBA 视角**（对照 skill `dba-schema-review` 12 条） | TechLead | **人类** |
| 涉及架构契约 / ADR / 系统设计 | 多轴评审 + **架构视角**（对照 skill `architecture-reviewer`） | TechLead | **人类** |
| 涉及鉴权 / 密钥 / 信任面 | 多轴评审 + **安全红线自查**（见 skill `security-redlines`） | TechLead | **人类** |
| 涉及性能热路径 | 多轴评审 + **性能轴**（先测量，附基线数据） | TechLead | **人类** |
| 涉及 UI / 前端页面 / 组件 | 多轴评审 + **UI 设计还原度轴**（对照 mockup，见 skill `ui-design-review`） | TechLead | **人类** |
| bug 修复（实现与 PRD 一致） | S3 TDD + S4 测试（**回归优先** + 不触发 PRD 变更） | TechLead | **人类** |
| bug 暴露 PRD 歧义 / 优化改行为 | 先过 **PRD 变更门（`prd-critic` + 人类确认）**，再走对应代码门 | TechLead | **人类** |
| 小队规则 / 标准 / agent 定义 / 流程 | 多轴评审 + **人类共识（两节点）**，自检对照 skill `review-checklist` 第六节 | TechLead | **人类拍板**，不自动合 |

> **溯源门（所有 `feat` / `fix` MR）**：建 MR 前先过 skill `mr-traceability` 的 **L1 机械检查**（标题前缀 / PRD 引用 / 关联单号），不过不建 MR。

## 三、S4 测试门的构成（谁产出、怎么算过）

> **S4 不复跑单测**。单测由 S3 的 Dev 在 runtime 执行并留证（命令 + 结果 + junit + 覆盖率）；S4 的职责是**审查证据 + 补强**，不是重跑。

S4 门禁 = 下列各项**全部满足**才算通过：

| # | 要件 | 判据 | 不过怎么办 |
|---|---|---|---|
| 1 | **AC → 测试证据映射** | 每条 AC 有明确归属的测试/用例 + 可回查证据 | 覆盖空洞 → 退回 Dev 补用例 |
| 2 | **通过率硬门** | P0 100% / P1 ≥95% / P2 ≥80% | 未达 → 缺陷登记，退回修复 |
| 3 | **P0/P1 回归覆盖 100%** | 改动未破坏既有功能，回归结果留证 | 未达 → 不通过 |
| 4 | **边界/异常用例** | ≥3 个，且有依据 | 缺 → 补测 |
| 5 | **结果复核（R1–R5）** | 无误判 PASS 遗留，证据优先 | 有疑 → 改判 FAIL 并写明原因 |

> 缺独立执行器的情况下，**S4 的「独立性」体现在审查与补强，而非复跑**：AC 映射查「有没有漏」，边界/回归查「够不够广」，复核查「判得对不对」。

## 四、两道门（区分「定稿」与「生效」）

| 门 | 含义 | 动作 |
|---|---|---|
| 门 1 · 合并定稿 | 评审通过 → 代码合进集成分支 | 人类 merge（agent 不碰） |
| 门 2 · 生效 | 改小队规则/流程/agent 定义的 MR，合并后还需同步到 Multica 才生效 | 人类跑同步脚本（见下） |

> **合并 ≠ 生效**：改 `agents/*.md` / `skills/*.md` / `squad-instructions.md` 的 MR，合并进仓后，还需执行同步脚本（`sync_dev_squad.py`）应用到 Multica 平台，才真正生效。合并只是版本化，不是应用。

## 五、分支策略（与 skill `gitlab-workflow` 对齐）

- **一个需求一条开发分支**：同一需求（如 `SCDE-550`）的规格 / 架构 / 实现 / 补强全部在**同一条开发分支**上迭代，**不按阶段新建多条分支**（杜绝 spec / arch / impl 各一条）。
- 开发分支默认从 `release` 切出；`release` 不存在 → 停下 @人类提供 base 分支，**绝不自己推导**。
- **MR 目标分支由人类提供（MR 前置门禁，blocking）**：建 MR 前必须先取得**人类明确给出**的目标分支；人类未给 → **不建 MR**，**绝不猜测**；已建 MR 一旦发现目标分支非人类所给 → **立即改指或关闭重开**。
- 分支相关一律上抛人类（base 与 target 都由人类给），agent 不自行推导。

## 完成判据（本 skill 视为已遵守）

- [ ] 变更类型已按第二节矩阵匹配，需叠加的门禁一项不漏；
- [ ] 一个需求一条开发分支（未按阶段新建多分支）；分支 base 与 MR target 均来自人类且可回查；
- [ ] 建 MR 前确认「存在 MR ⟺ 已过门禁」，未过门禁不建 MR；
- [ ] 未执行任何 merge 动作（合并一律人类）；
- [ ] 治理类改动已标「待人类批准」+ 附 post-merge 应用清单。
