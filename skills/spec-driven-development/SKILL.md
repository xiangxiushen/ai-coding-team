# 规格驱动开发（Spec-Driven Development）

## 是什么 / 何时用

先写规格（spec），经人类 approve，再写代码。规格是「我们要做什么、怎么算做完」的可评审契约，是测试和评审的依据。

**用**：任何超过 30 分钟 / 跨多文件 / 需求模糊的任务，动手前先写 spec。

## 规格六要素

1. **目标**：做什么、为什么、给谁用、成功长什么样。
2. **命令**：build / test / lint / run 的完整可执行命令（不是工具名，是命令）。
3. **项目结构**：源码在哪、测试在哪、文档在哪。
4. **代码风格**：一段真实代码示例胜过三段描述。
5. **测试策略**：框架、测试位置、覆盖要求、分层。
6. **边界**：Always（每次必做）/ Ask first（先问）/ Never（绝不做）。

## 假设显式化

写 spec 前先列出所有假设，让人类纠正：

```
ASSUMPTIONS I'M MAKING:
1. 这是 Web 应用（非原生移动端）
2. 认证用 session cookie（非 JWT）
3. 数据库是 PostgreSQL
→ 有误请纠正，否则我按此推进。
```

**写完 spec 立即停下**，等人类 approve，不在同一轮继续写代码。

## 反自我合理化

| 借口 | 现实 |
|---|---|
| 「太简单不用写 spec」 | 简单任务也要两行验收标准 |
| 「先写代码更快」 | 没契约的代码返工更贵 |
| 「需求我理解透了」 | 理解 ≠ 双方一致，spec 就是对齐点 |

## 完成判据

- [ ] 六要素齐全
- [ ] 假设已显式列出
- [ ] 人类已 approve spec
- [ ] 实现严格对照 spec，不擅自扩scope
