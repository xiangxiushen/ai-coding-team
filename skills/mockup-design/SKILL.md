# Mockup 设计（Mockup Design）

## 是什么 / 何时用

把 PRD / spec 变成**可评审的原型（mockup）**：页面布局、组件样式、交互流程、状态与响应式。mockup 是「设计意图」的载体，是前端实现与设计验收的共同基准。

**用**：需求含新增 / 改动的 UI、页面、组件、交互流程。

**不用**：纯后端 / 纯逻辑改动，无 UI 变化。

## 输入 → 输出

- **输入**：PRD 或 `spec.md`（功能需求 + AC + 数据约束）；项目设计规范 / Design Token（若有）。
- **输出**：mockup 产物（HTML 原型 / 设计稿文件），提交到约定位置（项目 `design/` 目录或指定的 mockup 仓），并给出可访问链接。

## 核心流程

1. **读需求**：通读 PRD / spec，列出全部功能点（FR）与验收标准（AC），标出每个功能对应的页面 / 状态。
2. **查现有**：先查项目里**是否已有可复用的 mockup / 设计组件**——有就直接复用并给链接，**不重画**。
3. **确认基准**：有设计规范 → 严格对齐 Token（色彩 / 字体 / 间距 / 圆角 / 阴影）；无规范 → 先问人类，不自造体系。
4. **设计**：页面布局 + 组件 + 交互流程 + 全状态 + 响应式（见下）。
5. **自查覆盖**：每个 FR / AC 都能在设计里找到落点，缺一不可。
6. **交互式验证（能测则测）**：产出 HTML 原型时，用浏览器实际打开，逐项点一遍交互与响应式断点，**不靠想象判断**。
7. **交评审**：产物交 UI 设计评审（`ui-design-review`）→ 通过后由人类确认；不通过则修订复评。

## 设计要点

### 组件与页面
- 复用成熟 UI 模式，**不凭空发明**新交互。
- 组件可复用、可组合，与设计系统一致。
- 信息层级清晰，用户一眼能找到重点。

### 全状态覆盖（最易漏）
默认 / 悬停（hover）/ 点击（active）/ 聚焦（focus）/ 禁用（disabled）/ 加载（loading）/ 错误（error）/ 空（empty）/ 成功（success）。

### 边界情况
超长文本、空数据、特殊字符、网络异常、权限受限。

### 响应式
- 桌面（≥1280px）/ 平板（768–1279px）/ 移动（<768px）三档至少各出图。
- 移动端优先：零横向溢出、可点区域足够、关键操作固定可见。

### 可访问性（WCAG 2.1+）
- 色彩对比度达标（正文 ≥4.5:1）。
- 键盘可达、焦点可见、屏幕阅读器语义正确。
- 不靠颜色单独传达信息。

## 要避开的坑

1. **过度设计**：简单场景别上复杂方案，优先成熟模式。
2. **为美观牺牲可用性**：低对比度文字、过小点击区域、隐藏关键操作。
3. **Dark Patterns**：不诱导用户做非自愿操作（如混淆取消 / 确认按钮）。
4. **只画理想态**：不考虑空数据 / 超长 / 异常。
5. **盲目推翻既有习惯**：用户已建立的交互心智不轻易改。
6. **无节制动效**：动画要有目的，且尊重 `prefers-reduced-motion`。

## 与实现的关系

- mockup 是**基准**：前端实现要对其负责，`ui-design-review` 按它逐像素验收。
- mockup 不是代码：**不把设计稿当作实现交付**；设计变更要同步给 Dev 与 Reviewer。

## 反自我合理化

| 借口 | 现实 |
|---|---|
| 「先画个大概，细节实现时再说」 | 细节缺失 = 评审无从对照，返工在后面 |
| 「只要好看就行」 | 覆盖不全的漂亮稿，等于需求没做完 |
| 「状态先不管」 | 空 / 错 / 加载态是 bug 高发区，必须画 |
