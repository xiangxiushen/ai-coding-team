# 测试驱动开发（Test-Driven Development）

## 是什么 / 何时用

先写失败测试，再写最小实现让它通过，最后重构。核心循环：**红 → 绿 → 重构**。

```
RED           GREEN            REFACTOR
写失败测试 ──▶ 最小代码让它过 ──▶ 清理实现 ──▶ (循环)
```

**用**：任何新功能、任何 bug 修复。测试一开始就过的，等于没测。

## 核心纪律

- **先写失败测试**，再写实现。红转绿才有意义。
- **Prove-It 模式（修 bug）**：先写能复现 bug 的测试 → 确认失败 → 修 → 确认通过 → 跑全量回归。
- **测试金字塔**：单测 ~80%，集成 ~15%，E2E ~5%。
- **DAMP 优于 DRY**：测试要自描述、每段独立成故事，不为去重牺牲可读性。
- **测行为不测交互**：断言结果，不断言内部调用顺序。
- **真实实现优先于 mock**：真实 > fake > stub > mock。mock 只用于慢/不确定/有副作用的外部依赖。
- **Arrange-Act-Assert**：安排 → 执行 → 断言，结构清晰。
- **测试名描述行为**：`rejects_empty_titles` 而非 `test_3`。

## 反自我合理化

| 借口 | 现实 |
|---|---|
| 「我手动测过了」 | 手动测试不持久，明天改就坏 |
| 「先上线后补测试」 | 后补 = 不补 |
| 「代码自解释」 | 测试才是规格 |
| 「跳过这条让套件绿」 | 跳过的测试 = 埋下的雷 |

## 完成判据

- [ ] 每个新行为有对应测试
- [ ] bug 修复含复现测试（修前失败）
- [ ] 全量套件用仓库自己的命令跑绿
- [ ] 测试测的是行为，不是实现细节
