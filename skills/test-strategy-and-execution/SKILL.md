# 测试策略与签核（Test Strategy & Sign-off）

## 是什么 / 何时用

验证实现是否满足验收标准（AC）、发现边界、防回归，最终给出可审计的测试结论。**只出测试结论，不改业务代码。**（融合 marvel QA 的 test-strategy → test-case → execute → sign-off 全链路）

**用**：拿到 Dev 的实现、spec 和 S3 单测结果后，做**证据审查 + 补强测试 + 签核**。

## 前提：单测在 S3 由 Dev 在 runtime 跑，S4 不复跑

- **单测（单元测试）由 S3 阶段的 Dev 在 runtime 上执行**（runtime 已装 JDK/Maven + Nexus 凭据），产出**命令 + 结果（total/passed/failed/skipped）+ 覆盖率 + junit 报告**作为证据。
- **S4 不复跑单测**——避免在无独立执行器的前提下产生「同一环境跑两遍」的伪见证。S4 拿 S3 的证据做**审查**，并以**独立补强**补上单测覆盖不到的面。
- 因此 S4 的核心不是「再执行一遍」，而是**质疑证据**：这条 AC 到底被哪个测试验了？断言够不够硬？边界漏没漏？改动有没有破坏既有功能？

## 测试策略（按风险分配投入）

```
          ╱╲          E2E (~5%)  关键用户流
         ╱  ╲
        ╱────╲       集成 (~15%) 跨边界：API/DB/文件
       ╱      ╲
      ╱────────╲     单测 (~80%) 纯逻辑，毫秒级
```

- 纯逻辑无副作用 → 单测（S3 产出）
- 跨边界（API/DB/文件）→ 集成测试（S4 补强）
- 关键用户流 → E2E（限关键路径）

## 一、用例约束三件套（硬规则）

| 约束 | 规则 |
|---|---|
| **输入依据必填** | 每条用例必须标来源（FR 编号 / AC 编号 / 接口契约 / mockup 页面 / PRD 章节）。**无来源的用例不得执行。** |
| **禁止捏造** | 不推测、不编造用例与预期值；未知场景**不生成**，单列「待确认场景」交 Product / 设计确认。 |
| **分层断言** | 断言必须分层：状态码 → 响应体结构 → 业务语义/错误码 → 集成副作用 → 持久化。**仅断言 HTTP 状态码视为不合格**，退回重写。 |

> 另：生成用例后必做**冗余合并**，在保持 100% 功能覆盖的前提下精简，避免用例数量虚高掩盖覆盖空洞。

## 二、通过率硬门 + 回归要求

| 项 | 门槛 |
|---|---|
| P0 冒烟 | **100%** |
| P1 核心 | **≥ 95%** |
| P2 次要 | **≥ 80%** |
| P3 边界 | 尽力 |
| **P0/P1 回归覆盖** | **100%** |

- 未达门槛 → **S4 门禁不放行**，缺陷入 `bug-N.md`（登记 / 定级 / SLA 见 `defect-management` skill）。
- P0 判定：无法完成核心流程 / 数据丢失 / 影响 >50% 用户 / 安全问题，满足任一即 P0。

## 三、AC → 测试证据映射表（S4 核心产物）

把「AC 全过」这句模糊结论，变成**可回查的证据链**：

| AC | 验证它的测试/用例 | 证据（命令 / 输出 / 报告链接） | 结果 |
|---|---|---|---|
| AC-1 … | `XxxTest#yyy` / `TC-001` | junit 报告 / 执行输出 | PASS / FAIL |
| AC-2 … | 需人工验证 | 操作步骤 + 截图 | 人工 PASS / FAIL |

- 每条 AC **必须有明确归属**；**找不到验证它的测试 → 立即退回 Dev 补用例**。
- 有自动化覆盖标 `PASS (automated)`；需人工确认标 `manual checkpoint`，**人工检查点绝不自动 pass**。
- 任何一条 AC 无法映射 → 视为**覆盖空洞**，S4 不通过。

## 四、结果复核（误判兜底，fail-closed）

自动执行/断言结论**必须经复核才能出门**，任一不过即退回：

| # | 检查项 | 不合格信号 |
|---|---|---|
| R1 | 步骤-证据一一对应 | 缺证据、重复、张冠李戴 |
| R2 | 证据内容正确 | 空白 / 加载中 / 报错页 / 未登录跳转 |
| R3 | 报告与证据一致 | 报告说 A、证据是 B |
| R4 | **结果状态复核** | 重点排查**断言过宽导致的误判 PASS** |
| R5 | **误判兜底** | **只要证据显示异常，即使脚本判 PASS，也必须改判 FAIL 并写明原因** |

> **证据优先于结论**：拿不准时以「有异常证据」为准，不以「脚本说 PASS」为准。

## 五、验收报告结构（对齐 mitabase）

`qa-report.md` 必备三件套：

1. **验收项表**：验收项 / 预期 / **证据（命令·输出·链接）** / 结果——**每行都必须挂可回查的证据**，无证据的验收项视为未验收；
2. **结论**：APPROVED / BLOCKED（任一 AC 未过即 BLOCKED）；
3. **遗留项**：未闭环缺陷 / 待确认场景 / 已知限制。

## 六、签核流程

1. 读 PRD / spec / spec 的 AC、S3 的证据（命令 + 结果 + junit + 覆盖率）。
2. 出 `qa-report.md`：AC 证据映射表 + 边界/异常用例 + 回归结果 + 结果复核 + 缺陷清单。
3. 全过（含通过率硬门 + P0/P1 回归 100%）→ 出 `qa-sign-off.md`（APPROVED），回报 Leader。
4. 有失败 → 出 `bug-N.md` 给 Dev（按 `defect-management` skill 登记定级），回报 Leader 等返工，返工后重跑 S4。

## 七、测试质量要求

- **测行为不测实现**：断言结果，不断言内部调用顺序。
- **DAMP**：每个测试独立可读，讲完整故事。
- **Arrange-Act-Assert**：结构清晰。
- **一个概念一个断言**：不把多个行为塞一个测试。
- **真实实现优先于 mock**：mock 只用于慢/不确定/有副作用的外部依赖。

## 反自我合理化

| 借口 | 现实 |
|---|---|
| 「测试过了就够」 | 测试必要不充分，不抓架构/安全/可读性 |
| 「S3 单测绿了，S4 不用看了」 | S4 的价值是**质疑**：AC 有没有被真正覆盖、边界漏没漏 |
| 「断言状态码 200 就行」 | 断言过宽是误判 PASS 的主要来源，必须分层 |
| 「边界情况不重要」 | 生产 bug 大多在边界 |
| 「手动点过了」 | 不持久、不可回归 |
| 「跳过这条让套件绿」 | 跳过的测试 = 埋下的雷 |

## 完成判据

- [ ] **AC → 测试证据映射表**已出，每条 AC 有明确归属 + 可回查证据
- [ ] 用例满足三件套（输入依据必填 / 无捏造 / 分层断言）
- [ ] 通过率硬门达标（P0 100% / P1 ≥95% / P2 ≥80%）
- [ ] **P0/P1 回归覆盖 100%**
- [ ] 至少 3 个边界/异常用例记录并测试

- [ ] 失败项有 `bug-N.md`（按 `defect-management` skill 登记 + 定级）
- [ ] 全过则 `qa-sign-off.md` APPROVED 已出
